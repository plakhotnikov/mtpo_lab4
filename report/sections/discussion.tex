\subsection{Анализ результатов}

\textbf{Аннотационный \mbox{@RestController}} предоставляет наибольшую гибкость в реализации идемпотентности, но требует ручной реализации фильтра и хранилища ключей. Этот подход наиболее распространён в production-системах благодаря явности и читаемости кода. Разработчик полностью контролирует обработку запроса, может добавить произвольную логику валидации, трансформации и обработки ошибок. Недостаток~--- необходимость писать и поддерживать больше кода.

\textbf{Функциональные эндпоинты} (WebMvc.fn) используют тот же механизм Idempotency-Key через общий фильтр, что демонстрирует важное архитектурное преимущество --- фильтры работают на уровне Servlet API, независимо от типа контроллера. Это означает, что один и тот же \texttt{IdempotencyFilter} обеспечивает идемпотентность как для \mbox{\texttt{@RestController}}, так и для \texttt{RouterFunction}. Функциональный стиль обеспечивает лучшую композиционность: маршруты можно комбинировать, вкладывать и переиспользовать программно, в отличие от аннотационного подхода, где маршруты привязаны к методам классов.

\textbf{Spring Data REST} автоматически обеспечивает ряд механизмов идемпотентности: \texttt{@Version} генерирует ETag, а unique constraints предотвращают дубликаты. Это минимизирует объём ручного кода --- разработчику достаточно определить JPA-сущность и репозиторий. Однако этот подход ограничивает возможности кастомизации: Idempotency-Key не поддерживается автоматически, а бизнес-логика добавляется через EventHandler, что менее гибко, чем прямое управление в Service-слое.

\subsection{Идемпотентность как конвенция: почему нельзя <<всё делать через GET>>}
\label{subsec:method-convention}

Изложенные выше свойства HTTP-методов (таблица~\ref{tab:http-methods}) могут навести на естественный вопрос: если \texttt{GET} и \texttt{HEAD} одновременно безопасны (safe) и идемпотентны, почему бы не использовать их для всех операций? Ответ принципиально важен для понимания природы идемпотентности: \textbf{свойства HTTP-методов --- это семантическое соглашение, а не техническое ограничение, накладываемое протоколом}. RFC 9110~\cite{rfc9110} определяет ожидаемое поведение методов, но сам по себе протокол не запрещает серверу изменить состояние в ответ на \texttt{GET} или проигнорировать идемпотентность \texttt{PUT}. Иными словами, \emph{фактическая} идемпотентность и безопасность целиком определяются реализацией на стороне сервера. Тем не менее, отступление от конвенции влечёт за собой ряд серьёзных последствий.

\begin{itemize}
    \item \textbf{Кэширование на промежуточных узлах.} Ответы на \texttt{GET} по умолчанию кэшируются браузерами, прямыми и обратными прокси, CDN, service worker'ами. Если \texttt{GET} меняет состояние, второй запрос клиента может быть обслужен из кэша и вообще не дойти до сервера --- операция <<пропадёт>>. Для \texttt{POST} и \texttt{PUT} такого кэширования по умолчанию не происходит.
    \item \textbf{Предварительная выборка и префетчинг.} Браузеры, поисковые роботы, антивирусные сканеры ссылок и системы link preview (например, в мессенджерах) свободно вызывают \texttt{GET} на любых обнаруженных URL. Если такой запрос порождает побочный эффект, возможны спонтанные изменения данных без ведома пользователя. Исторический пример --- эпизод с Google Web Accelerator, который проходил по ссылкам <<Удалить>>, реализованным через \texttt{GET}, и удалял записи пользователей.
    \item \textbf{Утечка данных в URL.} Параметры \texttt{GET} передаются в строке запроса и попадают в журналы веб-серверов, историю браузера, заголовок \texttt{Referer}, аналитические системы. Это делает \texttt{GET} непригодным для передачи чувствительных данных (паролей, токенов, платёжных реквизитов).
    \item \textbf{Тело запроса.} Согласно RFC 9110, \texttt{GET} формально может содержать тело, но его семантика не определена, и многие прокси, CDN и HTTP-клиенты тело у \texttt{GET} удаляют. \texttt{HEAD} тела ответа вообще не возвращает и пригоден только для проверки метаданных ресурса.
    \item \textbf{Повторные попытки и отказоустойчивость.} HTTP-клиенты, балансировщики и сервис-меши автоматически повторяют только те методы, которые спецификация объявляет идемпотентными. Если \texttt{GET} имеет побочный эффект, такой автоматический retry приведёт к множественному выполнению операции.
    \item \textbf{Наблюдаемость и проверяемость контракта.} API-шлюзы, системы мониторинга, тесты на соответствие REST-конвенциям (например, линтеры OpenAPI) исходят из стандартной семантики методов. Нарушение этой семантики делает систему непредсказуемой для сторонних интеграторов.
\end{itemize}

Таким образом, общепринятое соответствие между методом и типом операции~--- \texttt{GET}~для~чтения, \texttt{POST}~для~создания, \texttt{PUT}~для~полной~замены, \texttt{PATCH}~для~частичного~обновления, \texttt{DELETE}~для~удаления~--- является не техническим, а \textbf{инженерным требованием}, вытекающим из принципа наименьшего удивления~\cite{richardson2013restful}. Разработчик обязан реализовать эти свойства самостоятельно: \texttt{GET}-эндпоинт должен быть read-only, а не <<кажущийся>> read-only. В этом смысле тестирование идемпотентности --- это проверка не протокола, а соответствия реализации декларируемому контракту. Настоящая работа построена именно на этом принципе: для каждого метода проверяется не формальная корректность HTTP, а фактическая инвариантность состояния системы при повторных вызовах.

\subsection{Оптимистичная блокировка и границы её применимости для идемпотентности}
\label{subsec:versioning-limits}

Механизм \texttt{@Version}, продемонстрированный на примере Spring Data REST для сущности \texttt{Product}, часто преподносится как <<решение проблемы идемпотентности>>. Это упрощение требует уточнения: \textbf{версионирование в общем случае не обеспечивает идемпотентность; оно решает связанную, но иную задачу --- предотвращение lost update при конкурентных обновлениях}~\cite{fowler2002patterns, kleppmann2017designing}.

Различие становится очевидным при рассмотрении повторных запросов. Пусть клиент отправляет \texttt{PUT /products/42} с заголовком \texttt{If-Match: "3"}. Первый запрос успешно меняет версию $v = 3 \to v = 4$ и возвращает \texttt{200 OK}. Сетевой таймаут приводит к повторной отправке того же запроса с тем же \texttt{If-Match: "3"}. Второй запрос получает \texttt{412 Precondition Failed}, поскольку текущая версия уже равна 4. С точки зрения строгого определения идемпотентности это \emph{нарушение}: два одинаковых запроса дали разные результаты (200 и 412), несмотря на то что итоговое состояние ресурса идентично. Клиент, получивший 412, вынужден либо интерпретировать этот код как <<успех, просто повторно>>, либо выполнить дополнительный \texttt{GET} для перечитывания версии --- что усложняет протокол взаимодействия.

Идемпотентность \texttt{PUT} в нашей системе обеспечивается не аннотацией \texttt{@Version}, а самой семантикой метода \texttt{PUT} <<полная замена состояния>>: повторная отправка одинакового тела без \texttt{If-Match} приводит к одному и тому же финальному состоянию ресурса. \texttt{@Version} же решает \emph{ортогональную} задачу --- разруливание конфликта между двумя разными клиентами, одновременно редактирующими один ресурс на основе устаревшей версии.

\textbf{Частный случай, в котором версионирование действительно совпадает с идемпотентностью}, --- это PUT-операции, где запрос содержит ожидаемую версию не в заголовке \texttt{If-Match}, а в теле запроса как часть бизнес-смысла (например, <<применить эту дельту к версии 3>>). В такой модели повторный запрос с \texttt{expectedVersion = 3} после успеха первого вернёт тот же самый результат <<ожидаемая версия устарела>> для обоих повторов, что формально идемпотентно. Именно так работают многие системы event sourcing и CQRS. В нашей работе подобная схема \emph{не} используется: \texttt{@Version} на \texttt{Product} приведён исключительно как демонстрация того, что \textbf{Spring Data REST предоставляет optimistic locking <<из коробки>>} через заголовки ETag/If-Match, чтобы показать разнообразие механизмов, которые Spring-экосистема относит к тематике <<идемпотентности и повторяемости запросов>>. В production-системе, где действительно требуется идемпотентность \texttt{PUT} при retry, следует применять не \texttt{@Version}, а паттерн Idempotency-Key~\cite{ietf-idempotency-key, stripe-idempotency} --- именно он сохраняет \emph{ответ} первого выполнения и возвращает его без повторного исполнения операции.

Таким образом, \texttt{@Version} и Idempotency-Key --- дополняющие, а не взаимозаменяемые механизмы: первый защищает от \emph{двух разных} запросов от разных клиентов, второй --- от \emph{одного и того же} запроса, повторённого из-за сбоя сети.

\subsection{Значимость Testcontainers в тестировании идемпотентности}

Использование Testcontainers вместо in-memory баз данных (H2) имеет критическое значение для тестирования идемпотентности. Ряд механизмов зависит от особенностей конкретной СУБД:

\begin{itemize}
    \item \textbf{UNIQUE constraints} --- поведение при нарушении уникальности различается между H2 и PostgreSQL (разные коды ошибок, разная обработка транзакций).
    \item \textbf{Flyway-миграции} --- синтаксис SQL может отличаться (например, \texttt{gen\_random\_uuid()} специфичен для PostgreSQL).
    \item \textbf{Конкурентный доступ} --- PostgreSQL поддерживает уровни изоляции и блокировки, отличные от H2.
\end{itemize}

Singleton-паттерн Testcontainers (один контейнер на все тесты) обеспечивает баланс между точностью и скоростью: тесты работают с реальной СУБД, но контейнер запускается только один раз за сессию.

\subsection{Рекомендации для production}

На основе проведённого исследования сформулированы следующие рекомендации:

\begin{enumerate}
    \item \textbf{Всегда требовать Idempotency-Key для POST-запросов}, создающих ресурсы или выполняющих побочные эффекты. Это предотвращает дублирование при retry и является отраслевым стандартом~\cite{stripe-idempotency}.
    \item \textbf{Использовать optimistic locking} (\texttt{@Version}) для защиты от конкурентных обновлений. Это особенно важно для систем с высокой нагрузкой.
    \item \textbf{Устанавливать TTL} для ключей идемпотентности. Рекомендуемое значение --- 24 часа~\cite{ietf-idempotency-key}. Слишком короткий TTL не защитит от поздних retry, слишком длинный --- приведёт к росту таблицы ключей.
    \item \textbf{Хранить ключи} в той же СУБД, что и бизнес-данные, для обеспечения транзакционной консистентности. Альтернатива (Redis) обеспечивает лучшую производительность, но вводит риск рассогласования.
    \item \textbf{Тестировать с реальной СУБД} через Testcontainers~\cite{testcontainers}, а не с in-memory заменителями, для достоверности результатов.
    \item \textbf{Комбинировать механизмы}: Idempotency-Key для POST, @Version для PUT, UNIQUE constraints как последний рубеж защиты от дубликатов.
\end{enumerate}

\section{Заключение}

В данной работе проведено исследование и демонстрация тестирования идемпотентности REST API на базе Spring Boot. Разработано приложение с тремя кардинально различными типами контроллеров, для каждого из которых реализованы и протестированы механизмы обеспечения идемпотентности.

Основные результаты:
\begin{itemize}
    \item Формализована математическая модель идемпотентности HTTP-запросов с доказательством корректности паттерна Idempotency-Key.
    \item Реализован и протестирован паттерн Idempotency-Key с хранением ключей в PostgreSQL, применимый к любому типу контроллера через Servlet-фильтр.
    \item Продемонстрированы три кардинально различных подхода к организации REST API в Spring: аннотационный (@RestController), функциональный (RouterFunction) и автогенерируемый (Spring Data REST), каждый с собственным механизмом обеспечения идемпотентности.
    \item Разработано 22 интеграционных теста с использованием Testcontainers и PostgreSQL, покрывающих все аспекты идемпотентности для трёх типов контроллеров.
    \item Продемонстрировано критическое значение механизмов идемпотентности: при их отключении (профиль non-idempotent) система допускает дублирование данных и тройное списание при retry.
\end{itemize}
